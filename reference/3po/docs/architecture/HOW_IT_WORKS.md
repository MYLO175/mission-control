# How 3PO works: detailed reference

Use **Sources & searches** beneath a reply to inspect its starting context, the search terms and filters sent to lookup tools, pages opened, returned-record counts and completed or failed lookups. Queries are saved locally with the reply in a bounded history. Inspection starts no AI or source read. Current account/access choices gate query details; normal page/content updates do not erase this historical metadata. Page links open the current permitted page. Older replies retain their existing context details without invented search history. Source bodies, full tool/action arguments and model reasoning are not copied into the history.

Streaming displays provisional text using lightweight Stop, turn/account, storage and access metadata. Full context/evidence validation runs before and after model requests and around tool execution. It no longer rebuilds context pages or source projections for every text fragment. A completed model response remains necessary before tool execution or a completed reply; changed supporting evidence can reject completion and leave the displayed text marked partial. Lookup history is recorded only at read boundaries.

Standalone `hi`, `hey` and `hello` messages can start with a smaller configured-model request and low reasoning effort. It retains the guide, permitted conversation and complete applicable Assistant guidance; pending actions, outstanding questions, images, setup, Review, queued work and partial guidance use the full assistant. The initial round has one read-only option to open the normal policies and tools for the same captured turn if the human's instructions require them. This is a model response with normal streaming, Stop, ownership, completion and usage handling. Other requests keep their existing model and reasoning effort.

Chat preparation checks only background delivery identities that can enter its bounded history, refilling when an unavailable delivery exposes an older candidate. Exact history, shared delivery identities and source/page evidence remain checked. Review acknowledgements share one current evidence projection within each synchronous read, and rejected messages stop before source preparation.

## Finding and controlling context

Open **Context** from the assistant menu. Its sections can be collapsed, and Projects follows the same parent/subspace structure as your workspace. Each space appears immediately, even before its first AI summary. Short descriptions show your own project-purpose writing when present, otherwise a supported maintained synopsis. Space pages provide a child-description table, separate human description/instruction controls and expandable detailed context. Topics also have instruction controls before a maintained topic page exists.

The **3PO guide** explains where information lives. Ordinary chat starts with a compact stable version, then adds relevant pages and working changes. It can open a root space's child index and read deeper pages as needed. Human instructions flow down exact parent paths; child guidance applies more specifically, and unrelated branches stay separate. Heartbeats maintain changed factual descriptions while preserving human wording, evidence and history. Purpose questions are reserved for important unknowns that affect useful assistance; routine empty folders do not cause an interview.

Ordinary chat receives no automatic parallel list of original saved facts. The fact ledger remains behind the pages for evidence, correction history and heartbeat maintenance, and can be read explicitly when original detail is useful. Review conversations and the setup interview retain their purpose-specific record context. Sources & searches distinguishes original records actually supplied from evidence that validates the page context; older captures explain that they recorded those identities together. Additional evidence can also come from a page opened through a tool, without issuing a fact-edit target.

The guide lists **Your spaces**, **Your topics** and **Your instructions**, with a short description and a link for each. The visible topic/instruction lists and the AI map share the same route definitions. Topics include the life areas and retained recent context; instruction links open the existing Assistant, Projects, Reminders, Brief, Review and Calendar controls. Space/topic-specific guidance stays inside its own page. Directory descriptions explain where to look without copying private topic facts or policy bodies into the starting guide. Opening a link makes no AI request.

The guide is placed before changing context to support prompt-cache reuse. Context details records a fingerprint and size, and existing usage diagnostics retain provider-reported cached input. Those observations are separate from a guarantee of cache residency or response speed.

Chat history checks its exact page receipts against one fresh context projection per purpose, discarded before yielding. Confirmation lookup checks only saved confirmation candidates. A bounded local cache reuses canonical record formatting only after current eligibility checks and while the complete input value is unchanged; account or store revisions clear it. Collected source items compute their existing exact identity hash when created or when that identity changes, rather than repeating it during grouping, sorting and retention checks. Streaming access metadata stays cheap; full supplied-information checks run at request/tool boundaries. A validated `response.completed` accepts authoritative final text, tool output and usage without waiting for the HTTP connection to close; item completion or a partial reply alone cannot finish a request.

## 21 October: context pages as the primary memory interface

Open **PA menu → Context**, **Settings → Context → Open Context pages**, or an existing project's **Context** shortcut. Overview, project and topic pages hold readable Markdown with local version history. Working changes shows current permitted information awaiting consolidation. Instructions groups the assistant, project, reminder, brief, Review and Calendar guidance; existing saved preferences remain authoritative. Supporting facts and controls retains original evidence, corrections and learning controls.

Normal chat receives compact everyday orientation and a directory, alongside relevant page excerpts and working changes. The assistant can retrieve more with `read_context_page`. Briefs, email review/drafts, Review conversations and proposals, setup and retained placement work use the same purpose-specific page projection and exact supporting references. Canonical learning and correction still use original records; generated prose never becomes fresh evidence or action authority. Opening pages, displaying saved output and approving a prepared action make no context inference.

A scheduled heartbeat updates a bounded batch when relevant records change. An explicit Run heartbeat additionally works through the initial captured page backlog in bounded batches under that run's existing allowance. Later arrivals wait for the next cycle. A failed batch retains saved pages and pending work, and a quiet cycle needs no page-synthesis request. The consolidation model returns one typed result with short issued page choices and a page-specific evidence picker rather than copying opaque identities and quotations. 3PO resolves each ID to its original record/version and attaches the untouched text locally; invalid selections leave saved pages and pending changes intact. Calendar routing also reuses bounded existing human calendar guidance, with its original evidence and account/provider identities, without inventing separate purpose notes.

Before a brief or attention read uses a group of saved suggestions, it checks their page support against one current projection per requesting purpose. This shared projection expires at the end of that synchronous read; later checks rebuild it. Every suggestion keeps its own exact receipts, while large saved histories avoid repeatedly rebuilding the same source context.

## 16 October: one context path and one memory store

Chat, Review conversations and briefs now prepare relevant memory through the same local code. This preparation is not another AI. It filters records by the current account, permitted sources and usability, then selects relevant facts and related notebook anchors within each purpose's existing budget. It does not read Mail or WhatsApp itself. The existing AI sees those selected facts and uses its existing tools when it needs current source details. Naming email points it toward email; asking broadly can start with relevant memory and expand to permitted sources when needed. A stable human fact already supplied in context can be answered directly. An empty memory search advises trying another targeted wording before claiming nothing is known.

A short follow-up such as a timing/status question can reuse the immediately preceding human request as its search subject. A new subject does not inherit unrelated earlier context. Context details can show the preparation purpose, source hints and this follow-up use alongside existing fact IDs/tool names. These are input-selection receipts, not a record of the model's reasoning.

Older Review preferences have been converted into the same canonical memory used by current feedback and life facts. There is no separate live legacy preference lookup/editor. The conversion preserves original identity, account, direction and disabled state, saves an exact historical proof and removes the old store in one transaction. Unknown or unsafe conversions leave original data intact. Restoring the same old bytes cannot restore a forgotten or changed fact. Historical proof checks compare the current usable belief, allowing harmless organisation/review bookkeeping changes. Preferences and other memories remain different kinds of knowledge inside the same store; general writing instructions retain their existing app setting.

Retrieval remains bounded and local. It handles selected grammatical/spelling variants, explicit human-written abbreviations and distinctive terms; the AI can also reword a targeted search. It is not full semantic search. Relevant pending concerns now receive space in cross-source comparison rather than being displaced entirely by newer unrelated cards. Exact matching native edit/removal proposals can coalesce against the same captured target and baseline. Whether two new invitations describe the same situation still needs reasoning and can remain uncertain; similar names or titles never silently merge identities. Sources retain the originals, while learned memory retains concise facts and evidence references under the existing learning controls.

## 16 October: audit reliability repairs

Reminder completion validates the displayed item and modification revision before obtaining its full native baseline. Completion Undo checks exact saved original and detached-occurrence snapshots, including completion dates. Reminders reads have cancellation and a deadline; cancelling resumes the waiter and cancels the native fetch, with late callbacks ignored. Native operations distinguish a proven failure before any save from an attempted or unverified save. The former retains a durable failure identity/history and can be corrected; uncertain saves remain blocked from replay.

Personal storage uses a retained application writer lease, with an early check for already-running older copies. Cooperating repository writes serialize under per-store leases. Projects, native creation claims and action ledgers compare their loaded record with current saved bytes before writing. A stale owner cannot overwrite a newer claim or start its native operation. Older binaries do not implement this protocol, so release validation still checks and closes old copies before installation. Project/claim saves retain unknown additive fields by exact identity; transformations that cannot preserve opaque data safely are refused with original bytes intact. Project operation receipts no longer expire at 2,000 entries. Deleted history does not consume the active-item limit, and restoring a child restores its selected subtree rather than unrelated siblings.

Projects builds an ordered parent/child/progress index once per store revision and account/topic/Focus scope. Navigation, folder tiles, breadcrumbs, Tree and progress reuse it during hover, drag and layout changes. It is a derived cache, not new authoritative project data, and does not change drag/save guards, notes or page visibility.

Chat caches ordered ordinary history and separators between saved transcript revisions, projecting only the visible suffix and active reply while text streams. Source-backed brief rows still check current support on every observed read, including hidden deliveries. Ordinary live deltas do not rebuild history or move the viewport while the user reads earlier messages. Delivery-heavy histories retain a permission scan; this is not a general history-storage migration.

AI reply dependencies follow the facts actually supplied by selected context, successful memory reads and earlier replies. Unrelated source facts no longer become dependencies of every answer. Legacy traces narrow only when their exact history can be reconstructed; incomplete traces retain their conservative source gates. Native learning validates its issued source items and relevant permission choices, so an unrelated EventKit notification cannot pause unchanged Mail learning. Newly admitted WhatsApp learning scopes baseline cached content using durable permission generations and opaque chat membership. Existing pending versions and failed-claim pauses remain; explicit Review once is the bounded historical route. Foreground queues retain per-request/image bounds and recovery states without the retired request-count caps.

Partial Mail account discovery keeps failed-account caches and cursors while allowing healthy accounts to collect. Status-only WhatsApp updates make no message-snapshot persistence/publication, retaining edit/delete journal ordering for genuine content changes.

Review preparation now saves an opaque receipt for the exact Mail account, message and body/content version under the active registration. Reassessing the same email can still compare handling, confirmations and existing proposals, but cannot add another set of background suggestions or project tasks. The first preparation retains separate supported actions and destinations. New messages and changed source content remain eligible, with unchanged concrete actions still deduplicated. An exact validated replacement can supersede an existing concern; explicit human requests can revise or create through the ordinary foreground workflow. Approval, uncertain-save, dismissal and retirement records keep their original identities and outcomes. Project-parent identity and native occurrence/action identity are stable for duplicate comparison; their full current revisions remain mandatory at execution.

Legacy completed-pass receipts can migrate only when their saved assessed version and existing proposal match the current exact source assessment, independently of old context revision. A legacy proposal alone cannot prove all siblings were prepared, so incomplete or unverifiable historical batches retain action-level deduplication. Receipts contain hashes, no duplicated email text, and outlive ordinary source-cache pruning.
